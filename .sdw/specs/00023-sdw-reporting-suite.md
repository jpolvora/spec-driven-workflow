# Specification — SDW Delivery Reporting — Activity, Standup, and Spec Explanation

## Description

SDW records run state, step artifacts, a ledger, and telemetry, but it offers no reporting surface. Operators cannot produce a timesheet for a delivery day, a standup summary for the last 36 hours, or a plain-language explanation of what a specification delivered and how to test it. The data exists in several places, and each consumer currently reconstructs it manually.

This specification adds a read-only reporting suite: `report activity`, `report standup`, and `report explain`. Reports derive from run state, telemetry, the AC ledger, and git history; they never infer unavailable facts and mark missing evidence as `unknown`.

### Design Intent

Turn existing execution evidence into operational answers without creating a second data store. Reporting is a projection, not a source of truth: every value is traceable to a state file, event, ledger entry, or commit. Read-only behavior keeps reports safe to run at any time. JSON output supports automation while Markdown output remains human-readable.

## Acceptance Criteria

- AC1: The system shall provide a `report activity --date` command that produces timesheet entries for a delivery day.
- AC2: The system shall derive activity start from the earliest run artifact creation time.
- AC3: The system shall derive activity end from the later of the last pull request thread comment or the last delivery commit.
- AC4: The system shall provide a `report standup --hours 36` command that lists delivered, in-progress, and next items.
- AC5: The system shall provide a `report explain <spec>` command that shows status, delivered files, verification results, and manual test steps.
- AC6: The system shall make reporting commands read-only.
- AC7: The system shall support `--json` output for every reporting command.
- AC8: The system shall derive reporting data from run state, telemetry, the AC ledger, and git history.
- AC9: The system shall mark missing evidence as `unknown` instead of inferring values.
- AC10: If no delivery evidence exists for a date, then the system shall return an empty report with a zero exit code.
- AC11: The system shall document reporting commands, data sources, and output fields.
- AC12: The system shall add tests for activity, standup, and explain outputs.

## Notes

- Implementation surfaces:
  - `skills/sdw-orch/scripts/reporting.cjs` (new): data collection, date filtering, report rendering, and JSON output.
  - `skills/sdw-orch/scripts/sdw_orch.cjs`: `report activity`, `report standup`, and `report explain` subcommands.
  - `skills/sdw-orch/references/reporting.md` (new): command surface, data sources, fields, and unknown semantics.
- `report activity --date YYYY-MM-DD` output fields: date, spec slug, start, end, duration, delivery commit, PR URL, status. Start is the earliest artifact mtime in `{stateDir}/{slug}/{runId}/`; end is the later of the last PR thread comment timestamp and the last delivery commit timestamp. When no PR or thread data exists, end falls back to the last telemetry event and marks the source.
- `report standup --hours 36` output sections: delivered (completed or merged runs), in progress (active or paused runs), next (pending specs in the index). Each item names the spec, current step, last event, and blocking gate when present.
- `report explain <spec>` output sections: status and lifecycle, what the feature does, delivered files, verified and unverified acceptance criteria, tests observed, manual UI or CLI test steps, and out-of-scope items. Verification data comes from the ledger; missing ledger data is `unknown`.
- Read-only guarantee: reporting opens files for reading only and never calls state mutation helpers, git write commands, or provider mutation intents.
- Unknown semantics: `unknown` is a literal value, not an empty string or a guess. Reports include the reason (for example, `no telemetry`, `no ledger`, `no PR`).
- Empty report: a date with no runs returns a valid report with zero entries and exit code 0.
- Tests: add `tests/sdw_reporting.test.cjs`. Cover activity start/end derivation, fallback ordering, standup sections, explain sections, unknown marking, empty date, JSON output, and read-only behavior with a mutation-detecting fake.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Invoicing, billing rates, and client allocation | Activity reporting produces durations only |
| A web UI or dashboard | Reports are CLI and JSON surfaces |
| Cross-project portfolio reporting | Single-project scope |
| Automatic timesheet submission | Consumer-owned integration |
| Semantic summaries generated by an LLM | Reports must be deterministic and traceable |

## Validation & Observation Notes

### Telemetry & Observable Signals

- `report activity --date` prints one row per spec with start, end, duration, and source.
- `report standup --hours 36` prints three sections with counts.
- `report explain <spec>` prints status, delivered files, verified criteria, tests, and manual steps.
- Every `--json` output parses and includes the same fields as the text output.
- Unknown values include a reason string.
- A read-only test detects no state or git writes.

### Negative & Failing Test Scenarios

- Empty date: a date without runs returns zero entries and exit 0.
- Missing telemetry: activity falls back to the last delivery commit and marks the source.
- Missing ledger: explain marks verification as `unknown`.
- Missing PR: activity uses the delivery commit and marks `no PR`.
- Malformed state: the report skips the run and warns without crashing.
- Read-only violation: a fake writer that detects a mutation fails the test.
- Invalid date: a malformed `--date` exits non-zero with the expected format.
- Unknown spec: `report explain` for an unregistered slug exits non-zero and suggests `sdw-spec list`.
